# MC6839 floating-point linkage (scope / design)

Plan: replace the Microware-format `cfloats.a` helpers with the **MC6839** IEEE
FP package. MC6839 is IEEE 754 binary64/binary32 — the same format clang's
`double` uses on the host — so the compiler's constant emission (now fixed,
commit 3d60db3) already produces exactly the bytes MC6839 wants. This doc scopes
the runtime linkage; the shim runtime itself is the next step.

## The module

`ROM/Float09.bin` in the nfp09 repository
(`git clone https://github.com/markrvmurray/nfp09.git`; 8192 bytes) is a valid OS-9
module:

| Field | Value |
|-------|-------|
| Name | `FPO9` |
| Type/lang | `$B1` (USR-B, 6809 obj) — not a program; `F$Load`/`F$Link` work |
| Attr/rev | `$82` (reentrant, rev 2) |
| Size / CRC | `$2000` / good |

It's an OS-9 *multimodule*: after the 9-byte header is an entry table mapping
named entries to offsets (confirmed from nfp09's `romsrc/frnbak.s` and the binary):

| Entry | Offset from module base | Max stack |
|-------|-------------------------|-----------|
| `REG`  (FPREG)  | **`$3D`** | 155 bytes |
| `STAK` (FPSTAK) | **`$3F`** | 185 bytes |

Both are `BRA` into the register / stack front ends.

## Calling convention (register ABI)

`LBSR FPREG; FCB <opcode>` — the package reads the opcode through the LBSR-saved
return PC, advances it past the FCB, and returns to the byte after. A `JSR
[ptr]` works identically (also pushes the return PC). Args: pointers in U/Y/X,
FPCB pointer in D (see nfp09's `abi/nfp09-abi.s` for the authoritative ABI).

Gotchas (from the llvm-mc6809 Bug #162 notes):
- **`PSHS U,Y` before the call, `PULS` after** — the ROM's exit restores U/Y to
  their values *at the call*, and uses them as scratch internally.
- **FPCB control byte must be nonzero.** For double: `CTL = $29`
  (precision=double `$20` | NRM `$08` | round-nearest `00` | affine `$01`).
- **Verify opcodes against `equates.s`**, not docs. Key ones:
  `FADD $00  FSUB $02  FMUL $04  FDIV $06  FCMP $8A  FNEG $20`,
  int↔float `FFLTS $24 / FFLTD $26` and `FFIXS $16 / FFIXD $18`, `FMOV $9A`.
  A bad opcode silently dispatches into the wrong table.

## crt0 linkage (the plan)

A program that uses FP `F$Load`s `FPO9` from crt0:

1. `F$Load` (or `F$Link` if it's already resident) `"FPO9"` → `U` = module base.
2. `_fpreg = U + $3D`, `_fpstak = U + $3F` — store in data-area (Y-relative)
   globals beside `_flacc`.
3. Build an FPCB (5 bytes: CTL,ENB,ERR,SS,TRAPV) with `CTL=$29`.
4. On exit, `F$UnLink`.

The MC6839 module file (`fpo9`, from `Float09.bin`) must be installed where
`F$Load` finds it (e.g. `/dd/CMDS/fpo9`), or pre-loaded into the module
directory at boot so `F$Link` resolves it.

## Shim runtime (next step)

Keep the compiler's existing codegen (it emits `leax x,y; lbsr _dstack; leax
y,y; lbsr _ddiv; lbsr _dmove` with an `_flacc` accumulator). Replace
`cfloats.a` with wrappers that hold IEEE doubles in `_flacc`/the operand stack
and call MC6839:

| c3 helper | MC6839 op |
|-----------|-----------|
| `_dadd`/`_dsub`/`_dmul`/`_ddiv` | `FADD`/`FSUB`/`FMUL`/`FDIV` |
| `_dcmpr` | `FCMP` |
| `_dneg` | `FNEG` |
| `_itod` / `_dtoi` | `FFLTS`/`FFLTD` / `FFIXS`/`FFIXD` |
| `_dmove`/`_dstack` | `FMOV` / memory moves |

Each wrapper: `pshs u,y`; set up operand pointers + FPCB; `jsr [_fpreg,y]; fcb
<op>`; `puls u,y`; rts. Verify each op on `usim09batch` (bare 6809, no OS-9
boot) against known IEEE values.

Single precision (`float`, 4-byte) uses the binary32 ops / FPCB precision bits;
the compiler currently evaluates FP in double, so doubles are the priority.
